How it was measured, and what was not checked

Where the numbers come from, the conditions they were measured under, and what they can and cannot support. Raw records are under results/ in the repository.

Waveforms

Three open-source RISC-V cores: PicoRV32 running its bundled Dhrystone, SERV running its bundled Zephyr hello image, and biRISC-V running a bare-metal program written for this project (sorting, CRC32, matrix multiply, a division loop; its 6 results match the same source compiled natively). All simulated with Verilator 5.020, dumped once per clock cycle after the rising edge, two-state with no x or z. The two extra waveforms are longer runs of SERV and biRISC-V.

What is measured for each format

Size and correctness

  • One simulation writes both VCD and FST; pywellen reads them into a bit matrix. The VCD, the vcd2fst FST and the Verilator FST must give the identical matrix.
  • Every format is fully decoded after writing and compared bit for bit, plus SHA-256, against the original matrix. Anything that differs is discarded.
  • Home-made formats (bit-pack, video, tables) include the compressed signal-name and width table in their size.

The two read timings

  • One signal: one signal across all cycles. Five signals picked with a fixed seed.
  • One cycle: all signals at one cycle. Five cycles picked with a fixed seed.
  • Each read includes opening the file and is checked against the matrix. Fast reads run 3 times per sample, about 15 in total; reads over 1 s run 3 times. Medians are reported.
  • The reference is GTKWave's libfst reading the default FST in-process (via ctypes), with no subprocess or text parsing.

Measurement conditions

Laptop, Intel Core Ultra 9 185H, WSL2 Ubuntu 24.04 with about 7.5 GB of memory and 22 logical cores. Warm cache (files are read right after they are written).

Rounds one and two (2026-11-25 to 26): the machine was running two other projects at the same time. The load at the start of each row is in the loadavg column and went above 8. Read these timings for order of magnitude only.

Idle re-measurement (2026-11-26): the other two projects were archived, and the user turned turbo boost off (Windows reports both current and maximum clock as 2300 MHz, the base clock). The five waveforms ran one after another, never in parallel; the three original waveforms were re-simulated and their bit matrices matched round one by SHA-256. During the run I was still building this site on the same machine (editing files, occasionally opening a browser preview); load is still logged per row. Waveforms re-measured so far: . Every waveform on the site is labelled with the round its timings come from.

What this supports, and what it does not

      

        

          
Supported (within the range tested)

          
    
            
  • A dozen video layouts are all clearly larger than FST and much slower for one-signal reads, consistently across three designs and five lengths.
    • 
            
  • For the same content, Parquet with one column per signal is about 10× smaller than one column per time point; both were verified bit for bit.
    • 
            
  • A wide Parquet table reads all signals at one cycle faster than libfst, by 4× or more on all five waveforms.
    • 
            
  • Every size comparison is between bit-identical contents.
    • 
          

        

        

          
Not supported

          
    
            
  • Only three small RISC-V cores (2,381 to 9,728 bits). This does not extend to large SoCs, memory-heavy designs or gate-level netlists.
    • 
            
  • At most 2.6 million cycles, and that waveform goes quiet later on. Waveforms of tens of millions of cycles or gigabytes were not tested.
    • 
            
  • Two-state only, no x or z.
    • 
            
  • One clock, one sample per cycle. Multiple clock domains, glitches within a cycle and real timestamps are out of scope, and those are exactly where change-stream formats like FST shine.
    • 
            
  • FST was not tuned: one way of reading a cycle with libfst, default block size. The 4–12× figure may be on the high side.
    • 
            
  • It does not show that a wide table is a good waveform format: no hierarchy, no change stream, and writing requires expanding the whole waveform first.
    • 
          

        

      

    

  


  

    

      
Command-line tool

      

        
Run the same comparison on your own waveform. It reads a VCD or FST, writes several formats, verifies each bit for bit, and times both reads. Everything runs locally.


# in WSL / Linux, after setting up the environment (see README)
source scripts/common.sh
python -m wavebench.cli my_wave.vcd                 # default: 5 key formats
python -m wavebench.cli my_wave.fst --all           # adds VCD, x264, long tables, DuckDB…
python -m wavebench.cli my_wave.vcd --json out.json # save results

        
    
          
  • Two-state only: it stops with a message on x or z.
    • 
          
  • Sample times must be evenly spaced (for example once per cycle, timestamps 0, 10, 20…). Irregular waveforms are rejected rather than silently resampled.
    • 
          
  • Needs vcd2fst / fst2vcd (GTKWave), FFmpeg, pyarrow, pywellen. Intermediate files go to a temporary directory and are deleted afterwards (--keep keeps them).
