Would simulation waveforms be smaller stored as video?

No, and not by a small margin. A digital waveform is a huge black-and-white image in which most bits stay the same from one cycle to the next, which looks like a perfect job for a video codec. I measured it on three open-source RISC-V cores: video loses to FST on size everywhere, and does not even beat naive bit-packing plus zstd. It wins exactly one thing: jumping to a point in time.

Put time on the rows, signals on the columns

Earlier work, vcd2df (arXiv 2505.06470), also stored waveforms as Parquet and found the files larger than VCD. The cause is orientation: it uses one column per time point. With the same content and the same compression, that orientation is × larger. A columnar format needs long columns to pay off.

Try it on your own waveform

The repository has a small command-line tool: give it a VCD or FST and it reports the size and both read times for several storage methods, each verified bit for bit. It runs locally and uploads nothing.

python -m wavebench.cli my_wave.vcd
python -m wavebench.cli my_wave.fst --all --json out.json

Limits: two-state waveforms only (no x or z), with evenly spaced sample times. Setup and usage on the method page.

There is no in-browser “upload and measure”: reading FST, encoding FFV1 and writing Parquet would all need C libraries compiled for the browser, and timings measured there would not be comparable with native ones. It would be a demo, not a measurement.
